這是一份以 RDNA 3.5 / GFX11.5 為主體的繁中技術 Wiki。從 ISA 的程式可見行為，向下拆解 WGP、CU、SIMD32、wave、pipeline、暫存器及 cache；再向上連到 HIP、LLVM codegen、指令排程、software pipelining，最後用 LLM inference 的 GEMV、GEMM、attention 與量化做驗證。

如何看證據

  • 官方規格：ISA 文件的定義，或明確標示產品的 AMD 硬體表。可作語意依據；不代表完整公開每個 pipeline stage。
  • 編譯器實作：LLVM 原始碼、target feature、pass 順序。它解釋特定版本的行為；不是硬體量測報告。
  • 推導模型：roofline、latency hiding、occupancy 上界及排程示意。假設寫在公式旁；不能拿示意的 cycle 當晶片實測。
  • 本機驗證：只對實際完成的 compile／assemble／disassemble 作標記；本專案未執行 GPU kernel 或效能 benchmark。

架構與 target 身分

WGP / CU / SIMD32

官方規格

一個 work-group 的家，不等於一個 SIMD。

計算工作由 host 提交，command processor／dispatch 路徑將工作送往 shader array。WGP（Work-group Processor）有兩個 CU；每個 CU 有兩個 SIMD32，所以每 WGP 有四個 SIMD32。CU 的兩個 SIMD32 共用一條通往記憶體的路徑。SIMD32 是執行向量運算的硬體；wave 是其上的執行上下文，並不是另一個實體核心。

來源：RDNA 3.5 ISA §1.1–1.2，pp.3–8。

來源：LLVM Memory Model GFX10–GFX11。

ISA、target、SKU 是三個不同層級

層級 例子 決定什麼
ISA 家族 RDNA 3.5 / GFX11.5 指令語意、編碼及執行模型
LLVM target gfx1150 / gfx1151 支援 feature、資源模型、codegen 差異
產品 SKU Radeon 890M / 8060S 啟用 CU 數、時脈、記憶體介面、cache 容量

官方 GPU 表列 Radeon 890M（例如 Ryzen AI 9 HX 370）為 gfx1150、16 CU、2 MiB L2；Radeon 8060S（例如 Ryzen AI Max+ 395）為 gfx1151、40 CU、2 MiB L2、32 MiB Infinity Cache。相同 gfx1151 也有 32 CU 或 16 CU SKU。不能把 40 CU 硬編碼成 gfx1151 的普遍常數。

來源：AMD GPU specifications，AMD Ryzen APUs 表。

CU mode / WGP mode

  • CU mode：同一 work-group 的 waves 位於同一 CU（兩個 SIMD32）；LDS 分半服務兩側。
  • WGP mode：同一 work-group 可分布於整個 WGP 的四個 SIMD32，並共用 LDS。
  • 每 WGP 128 KiB LDS，不代表單一 work-group 可配置 128 KiB：ISA 規定每 work-group 上限 64 KiB。啟動上限亦應查 runtime device properties。

來源：RDNA 3.5 ISA §1.2.2.1、§2.3，pp.7、11–12。

Wave、lane 與控制流

Execution state

官方規格

一份 PC，很多份資料。

一個 wave 擁有程式計數器、scalar state、vector registers 與執行遮罩。wave32 有 32 個 work-items；wave64 有 64 個。SGPR 值由整個 wave 共用；同一 VGPR 編號則代表各 lane 自己的 32-bit 值。這就是為什麼 uniform address 可以走 scalar path，而每 lane 的 index 通常需要 vector path。

來源：RDNA 3.5 ISA §2.1、§3，pp.9–17。

狀態 作用 常見誤解
PC wave 的控制流位置 不是每 lane 各跑一條獨立 PC 流
EXEC 決定參與向量運算／向量記憶體操作的 lanes mask 掉的 lanes 不會自動釋放 VGPR
VCC 向量比較或 carry/borrow 的 bit mask 不等於整個程式的 active mask
SCC scalar 條件碼 不是 32 個 lane 的比較結果
SGPR uniform scalar state SGPR 和 VGPR 不是同一份儲存池
VGPR per-lane values v7 不是整個 wave 只有 4 bytes

Wave64 如何跑在 SIMD32 上？

ISA 說明：wave64 的 VALU 及 VMEM 類指令通常分低 32／高 32 兩次 issue；SALU、SMEM、branch 與 message 則不因 wave64 而重複發射。某些全 inactive half 可以略過，但有記憶體計數與寫 scalar state 等例外。兩半之間也可能穿插其他 wave 的指令。

因此「wave64 = 所有指令都慢兩倍」錯誤；「wave64 = 兩個完全獨立 wave32」也錯誤。wave size 是編譯／啟動模式，不由當下 active lane 數自動切換。

來源：RDNA 3.5 ISA §2.1，pp.9–10。

Divergence 的真實代價

對 lane-varying 分支，compiler 可利用 EXEC、保存遮罩與控制流轉換，使不同 lanes 在各自遮罩下執行。若 wave 中同時存在兩條分支，通常得付出兩條路徑的執行成本，而不是免費平行。uniform 分支可避免這種 lane 分裂。詳細 lowering 隨程式、最佳化和版本而變。

LLM 對應：不整齊的尾端 tile、變長序列、稀疏／MoE routing 會造成 partial waves 或不同工作量。先看 mask 的利用率與 work distribution，再比較 wave32／wave64。集合運算（shuffle、WMMA、barrier）要滿足各自的 participation 條件；不能因為某 lane 的輸出不用就讓它錯誤地提前退出。

延伸來源：LLVM AMDGPU divergence 與 execution model · AMD WMMA 的 wave participation 與資料映射。

微架構 pipeline

Latency / throughput / issue

推導模型 公開限制

「在 pipeline 裡」不是「正在使用 ALU」。

理解 kernel 時，可用以下概念分解：instruction fetch → decode／wave eligibility → operand read／register cache → execution unit → forwarding／writeback。不同路徑（SALU、VALU、matrix、memory、LDS）有不同資源與完成條件。這不是 AMD 公開的逐 stage 實體 pipeline；本 Wiki 不宣稱每一段各需一個 clock。

ISA 明確指出，GPU 透過保留大量進行中的 work-items、讓運算和記憶體存取重疊，隱藏 latency。精確 queue depth、所有 bypass 路線、仲裁政策與每條 opcode 的 latency 矩陣，不能只從 ISA 推定。

來源：RDNA 3.5 ISA §1.2.1，p.6。

必須分開的四個量

量 意義 怎麼看
Latency producer 到 consumer 可安全使用結果的時間 dependent chain
Reciprocal throughput 在獨立工作充足時，相鄰操作的平均間隔 independent streams
Issue eligibility wave 現在是否可發射下一指令 dependencies、wait、資源 availability
Occupancy 同時駐留的 wave／work-group 數 metadata + runtime resource 限制

高 occupancy 不等於高 issue rate。全部 waves 都在等 DRAM，或都擁有相同長 dependency chain，ALU 仍會閒置。反過來，低 occupancy 但單 wave 有足夠 ILP、資料重用高，也可能較快。

有來源的 cycle，與沒有來源的 cycle

RDNA 3.5 ISA §6.8（p.54）明列 scalar FP operations 的 SALU latency 為 4 cycles，其他所述 scalar operations 為 2 cycles，並說明 SALU 保持順序與 forwarding／stall 以確保結果。不要把這個數字泛化為所有 instruction 的 issue interval，也不要混同 §5.7 所述常見 SALU issue 行為。

來源：RDNA 3.5 ISA §6.8。

Latency hiding 的玩具模型

若某 dependency 的 latency 為 L，每 I cycles 可發射一個獨立操作，想讓該路徑連續忙碌，粗略需要 ceil(L / I) 個獨立操作在途。獨立性可以來自同 wave 的 ILP，也可來自其他 waves。這不是 occupancy 計算式：issue width、不同單元、RF port、cache miss、queue cap 都可能先成為限制。

LLM 對應：GEMV 常受 weight load 限制；GEMM 可能受 WMMA 或 LDS staging 限制；dequantization 可能把瓶頸轉成 integer VALU、shuffle 或 VGPR 壓力。看見 ALU 空洞時，不應立即假設是時脈不夠。

延伸來源：LLVM AMDGPU scheduling 入口。

Register file、快取與 occupancy

Physical vs logical resources

官方規格 編譯器實作

多留一個 tile，可能少住一整個 wave。

VGPR 的成本是 per-lane。以 wave32 為例，使用 r 個 32-bit VGPR／lane，未計 allocation granularity 時，每 wave 佔 r × 32 × 4 bytes。register pressure 是同一時刻 live 的值；宣告變數多不一定壓力高，變數數量少但跨長距離存活也可能很貴。

ISA §3.3.2 指出一般配置粒度為 wave32 16 個／wave64 8 個；對 1536 VGPR／SIMD 的裝置，為 wave32 24 個／wave64 12 個。這裡的 1536 是以 wave32 向量槽位衡量的實體容量，不是 shader 可以直接命名 v1535。ISA 的 shader 可用 VGPR 數上限另為 256。

來源：RDNA 3.5 ISA §3.3.2.1，p.17。

gfx1150 vs gfx1151

LLVM target model 將 gfx1151 歸到較大的 VGPR file 配置；常用解讀是 gfx1150 128 KiB／SIMD32，gfx1151 192 KiB／SIMD32。乘以每 WGP 四個 SIMD32，對應 AMD 產品表的 512／768 KiB VGPR file。看到表格的 KiB 必須先確認 aggregation 層級，不能當成每 lane 或每 CU 的容量。

來源：LLVM 21.1.0 AMDGPU target definitions · AMD APU 規格表 · Chips and Cheese 對 gfx1150／1151 的 LLVM 解讀（次級）。

只看 VGPR 的上界示例，不是 occupancy 承諾

對 1536-slot 的 wave32 配置，若 r = 73，以 24 向上取整為 96；floor(1536 / 96) = 16。若 r = 97，則配置 120；floor(1536 / 120) = 12。很小的 live-range 變化就可能跨越門檻。真實 resident waves 還受 wave-slot、LDS、work-group 大小、配置模式、barrier 資源及 compiler/runtime 設定限制；不能直接把上述數字當 occupancy。

Register cache 不是 L0 data cache

Register file 存程式可見 register；operand／register cache 減少 RF 存取壓力；vector data cache 快取的是記憶體地址對應資料。ISA VOPD 規則明列 四個 VGPR banks 及各 source-position 的 cache read ports。這是「多一個獨立 FMA 也未必能 pair」的原因之一。

來源：RDNA 3.5 ISA §7.6，p.70。

s_singleuse_vdst：不要只看名字猜語意

這是一個必須標示歷史版本的案例，不是本機工具鏈可用的調校開關。LLVM 19.1.0 的 pass 描述為：標記產生 single-use VGPR 值的 VALU region；若值在 VGPR writeback 前已 forwarded 給 consumer，硬體可跳過該次 VGPR write。它不是釋放整個 wave VGPR，也不增加可配置容量，更不是「不快取下一條指令的所有 inputs」。當時 pass 預設也為關閉。

來源：LLVM 19.1.0 single-use pass · 當時的預設開關。

之後 commit 396f6775 移除了 feature、pass、指令定義及測試；本版核對的 LLVM 21.1.0 與主線 SHA 未恢復，本機 ROCm 7.2.2 assembler 在 gfx1150／1151 也回報 invalid instruction。本次 AMD 70649 PDF 未列此 mnemonic。這能證明所查工具鏈不支援，不能單獨證明 silicon 不存在該編碼，更不能猜測移除原因。

來源：LLVM 移除 commit／PR #109769 · 本機對照 source。

Spill 的代價

VGPR 壓力過大可能 spill 到 scratch/private memory，產生額外 memory traffic、地址運算及 waits。SGPR spill 亦可能先經 VGPR lanes，不能把所有 spill 視為同一種路徑。調整 unroll、tile 與 stages 後，務必一起檢查 VGPR count、scratch bytes 和反組譯，而不只看 source code 是否「更平行」。

來源：LLVM AMDGPU register allocation 與 private address space。

Cache、LDS、TLB 與 UMA

The data journey

官方規格

四種不同的「local」，不要混在一起。

名稱 對應 存取特性
Register SGPR / VGPR compiler 分配，沒有一般 load/store address
Shared / local address space LDS work-group 共用的顯式 scratchpad
Private / scratch thread-private spill／stack 可能位在裝置可存取的記憶體，並非 LDS
Unified memory APU 共享實體 DRAM 等系統概念 不等於零同步成本或無限頻寬

來源：LLVM AMDGPU address spaces。

資料路徑與共享範圍

GFX10–GFX11 memory model 將 vector L0 定義為 per CU，scalar L0 為 per WGP；vector/scalar L0 透過同一 SA 的 L1，L1 再使用整顆 GPU 共享的 L2。scalar 與 vector L0 不互相 coherent；compiler 對 scalar loads 使用情境有額外限制。MALL／Infinity Cache 的存在與容量必須查 SKU，不能假設所有 RDNA 3.5 APU 都有。

來源：LLVM GFX10–GFX11 Memory Model · AMD GPU 規格。

LDS bank：本代是兩組 32，不是模糊的一個 32

ISA 詳細章節說明：128 KiB／WGP，64 banks，分成兩組各 32 banks，各組與一對 SIMD32 關聯；每 bank 是 512 × 32-bit 的 1R/1W RAM。文件術語表的「32-bank LDS」是簡略敘述，不能蓋過 §12.1 的完整組織。每 work-group 配置上限仍是 64 KiB。

同時存取映到相同 bank 的不同資料，可能串行化。常見 (address / 4) mod 32 只能作單組 32-bank、DWORD 存取的教學模型，不是所有寬度、WGP mode 與指令的完整映射公式。padding／XOR swizzle 必須用真正 lane-to-address mapping 檢驗；不要把 NVIDIA shared-memory 的細節直接套過來。

來源：RDNA 3.5 ISA §12.1，pp.120–121。

Coalescing、reuse 與 TLB

  • 連續 lanes 存取連續地址通常能減少不必要的 memory transactions；實際效果仍受對齊、向量寬度、遮罩與頁邊界影響。
  • LDS staging 的價值在於重用和交換資料。資料只用一次時，額外 global → LDS → register 路徑可能反而更貴。
  • TLB 快取地址翻譯，不是 weight data。大範圍稀疏 stride、碎片化 allocation、page migration 都可能讓 latency 增加。本文不提供未經公開驗證的 gfx1151 TLB entry 數。

APU 共享 DRAM，不代表任意 pointer 都可安全共用

ROCm 系統文件將 GPUVM、GTT／TTM 描述為映射／資源管理問題。CPU 與 GPU 共用實體 DRAM，仍有 allocation API、cacheability、page residency、可見性及同步的差異；「zero-copy」也不等於 zero traffic。調大 memory limit 只能改善容量可用性，不會提高 DRAM bus 頻寬。預留 OS／CPU 空間，依實際 kernel、driver、ROCm 版本配置，不照抄全機 RAM 的上限。

來源：AMD RDNA3.5 system optimization。

Operand 怎麼讀？

v_fma_f32 v0, v1, v2, v3 概念上是逐 lane 的 v0 = v1 × v2 + v3，受 EXEC 影響。s[4:5] 常是兩個 32-bit SGPR 構成的 64-bit 值；v[8:11] 是連續 VGPR 範圍。instruction modifiers、literal、operand type 與 encoding 的可用組合，都會限制 compiler 能否產生想要的格式。

VOPD 是 encoding，不是「自動兩倍快」

VOPD 在一條指令內打包 X／Y 兩個 VALU 操作，僅對 wave32 合法。不是任意兩條鄰近指令在 runtime 自動合體。compiler 要先證明可 pair，完成編碼，硬體才按 paired instruction 執行。

ISA 的硬限制包含：兩個操作獨立；destination 一奇一偶；SRCX0／SRCY0 的 VGPR bank 不同，SRCX1／SRCY1 亦如此（特定 op 有例外）；若兩者都使用 SRC2，兩個 SRC2 一奇一偶。每個 component 最多一個 SGPR；整組允許至多兩個 SGPR、或一個 SGPR 加一個 literal、或兩者共用同一 literal；不能使用 DPP。完整合法性還要對照各 opcode 的 operand 規則。

來源：RDNA 3.5 ISA §7.6，pp.70–71。

# 概念比較，不是可直接組譯的程式
兩個獨立 accumulator： a0 += x0*y0 ; a1 += x1*y1
  → 有機會形成合法 VOPD（仍需滿足 opcode 與 register bank 限制）
同一 accumulator chain： a += x0*y0 ; a += x1*y1
  → 第二個依賴第一個的新值，不能當作獨立平行 pair

增加獨立 accumulator 有機會提高 ILP 或 pairing，但同時提高 VGPR pressure。最終要看反組譯是否出現 v_dual_*、分配到多少 registers、是否 spill，並用 benchmark 比較；不是在 C++ 寫兩行 FMA 就保證 VOPD。

來源：LLVM 21.1.0 VOPD formation pass。

WMMA 與 matrix fragments

Wave-level matrix arithmetic

官方規格

一條 WMMA 是整個 wave 合作，不是每 lane 各算一塊矩陣。

RDNA 3.5 的 v_wmma_* 以 VOP3P 編碼，執行 D = A × B + C。ISA 表 33 列出 16×16×16 的 FP16、BF16 輸入，FP16／BF16／FP32 accumulator 組合，以及 IU8／IU4 輸入、I32 accumulator 組合。不能因為文件寫 AI acceleration 就假設有 RDNA 4 的 FP8 指令或 CDNA 的 MFMA／AGPR 模型。

來源：RDNA 3.5 ISA §7.9，pp.74–77。

8192 operations，不是 8192 clocks

16×16×16 tile 有 16 × 16 × 16 = 4096 個 multiply-accumulate；以乘、加各一 FLOP 計算，為 8192 FLOPs／matrix operation。這是數學操作量，不是 latency、issue interval，也不是每 lane 的工作量。整數形式應稱 integer operations，不稱 floating-point FLOPs。

資料映射比 builtin 名字更重要

對本代 WMMA，A／B 的 lane 0–15 資料須複製到 lane 16–31；wave64 還需複製到 32–47、48–63。FP16／BF16 A、B fragments 各需 8 個 VGPR／lane；wave32 的 C／D 通常各需 8 個，wave64 則 4 個。C／D 可以重用同一 accumulator，並非每次都必須同時保留兩份。

Register fragment 的 row／column mapping，不等於使用者陣列在 DRAM 的排列：global loads 的 indexing 可以轉換佈局。寫 kernel 時要列出 lane, register, subword → matrix(row,col)，再證明 load/store 配置正確。

來源：AMD WMMA guide（RDNA 3；RDNA 3.5 ISA 亦明確連到此指南） · AMD matrix instruction calculator。

隱藏在 accumulator 以外的成本

  1. Global → VGPR／LDS 的資料搬移、轉置或 swizzle。
  2. A／B replication 與 fragment registers；多 stage 會把它們變成更多 live values。
  3. 分塊邊界、非 16 倍數的 padding／mask；小 M 的利用率可能很差。
  4. Output conversion、epilogue fusion、activation／bias 與 stores。

WMMA hazard 不可用通則掩蓋

ISA §7.9.1 指出：若前一 WMMA 的 D 和下一 WMMA 的 A／B 重疊，中間需要 一個 V_NOP 或無關 VALU，這是正確性要求。常見 D→C accumulator continuation 與 D→A/B 的 hazard 不同；表內也區分「正確性必需」和「只避免 stall」的情況。不要用「硬體會處理所有 ALU dependencies」就跳過特例。

來源：RDNA 3.5 ISA §7.9.1，p.77。

Three different guarantees

官方規格

等到 load，不等於等到其他 wave。

同步至少要分成三件事：本 wave 的非同步操作完成、多 wave 在同一點集合、以及不同執行單元看見正確版本的記憶體內容。wait counter、barrier、memory ordering／cache management 解決不同問題，不能互換。

LDS producer / consumer 範式

# 語意示意：實際等待與 cache 序列由 compiler 依 target 產生
所有參與 threads 將本 tile 寫入 shared/LDS
  → 確保對應 LDS 操作完成
  → work-group barrier

  → 確保 reads 完成後使用 registers
  → 再次集合，才可覆寫仍可能被別人讀取的 buffer

HIP 程式應使用適當的 __syncthreads() 與正式 memory-model API，並確保需要同步的 threads 都到達它。不能把 barrier 放在只有部分 threads 執行的資料相依分支，卻期望全 group 正常集合。跨 work-group 多用另一個 kernel dispatch 或適用的同步機制，不自行建立可能因 occupancy 而死鎖的全域 spin barrier。

s_delay_alu 為何不同？

ISA §5.7 說它是 optional 的 ALU scheduling 輔助：描述與較早 VALU／TRANS／SALU 的依賴，由硬體決定需要的延遲；有足夠 independent instructions 就不必加。它可能與前一指令平行執行，不應把每個 delay mnemonic 都算成固定一個 bubble。另有 WMMA 特例與其他 hazard instructions，請對照上一章與 compiler passes。

來源：RDNA 3.5 ISA §5.7 · LLVM SIInsertWaitcnts 的保守分析限制。

Instruction scheduling

Pressure-aware, not cycle magic

編譯器實作

先有依賴圖，再談把 load 往前搬。

Machine scheduling 將指令依 dependency DAG 排序，在真實資料依賴、memory ordering、資源限制下，選出較好的順序。pre-RA 看 virtual registers、live ranges、ILP 與 register pressure；post-RA 已知 physical register placement，能針對 bank／pairing 進一步重排，但自由度也受 register reuse 的依賴限制。

LLVM 21.1.0 的 AMDGPU 一般 fallback 是 createGCNMaxOccupancyMachineScheduler，亦有 max-ILP 等策略。名稱不代表「無條件把 occupancy 拉滿」：實作會綜合可達 occupancy、pressure limits、重新排程與放寬門檻等啟發式。

來源：AMDGPUTargetMachine.cpp · GCNSchedStrategy.cpp。

相關 passes 的概念順序

pre-RA MachineScheduler
 → register allocation / rewriting（含 AMDGPU 的分段處理）
 → post-RA MachineScheduler / VOPD pairing mutation
 → GCNCreateVOPD
 → SIMemoryLegalizer / SIInsertWaitcnts
 → 其他 clause / branch / mode / peephole 處理
 → stand-alone hazard recognition / SGPR hazard handling
 → AMDGPUInsertDelayAlu

這是上述固定版本一般最佳化路徑的節選，不是各 O-level、ROCm fork 或新舊 pass manager 的完整通用順序。VOPD formation、wait insertion、delay insertion 各有職責；post-RA scheduler 本身並不能涵蓋所有跨 scheduling region 的 hazards。

來源：固定 LLVM target pipeline。

Scheduler model 不是 silicon spec

gfx1150／gfx1151 在固定版本同用 GFX11SpeedModel，但 features／VGPR 容量不同。SISchedule.td 的數字例如 WriteFloatFMA=5、WriteVMEM=320、WriteBarrier=2000 是排程成本／latency 模型參數，絕不能報成「APU DRAM 固定 320 cycles」或「barrier 一定 2000 cycles」。IssueWidth=1 也不代表 VOPD 無法做兩個 component operations。

來源：Processor model mapping · GFX11 scheduling model。

「提前 load」的雙面刃

短 live range： load A → wait A → compute A → load B → wait B → compute B
增加重疊：     load A → load B → wait A → compute A → wait B → compute B

第二種把 B 保留得更久，可能隱藏 latency，也可能增加 VGPR 和在途請求；若 compiler 無法證明 alias safety，重排還會受限。restrict、alignment 等只能在程式真的滿足契約時使用，不能為了速度虛假宣告。

調校目標：在正確性下縮短關鍵路徑、保留有用的 ILP／MLP，同時不越過昂貴的 register／LDS 門檻。比較時應列出：相同 kernel shape、最終 opcodes、resource metadata、動態 kernel time。最少的 s_waitcnt、最多的 VOPD 都不是單獨的勝利條件。

來源：LLVM scheduling strategy · Delay ALU 使用模型計算相依延遲。

Software pipelining

Overlap iterations, not just instructions

原理示意 版本核對

同時載入明天的 tile，計算今天的 tile。

software pipelining 將不同 iteration 的工作重疊，產生 prologue（填入）、steady-state kernel loop（穩態）與 epilogue（排空）。它不同於把單一 basic block 的 instructions 重排，也不同於單純複製迴圈本體的 unroll。Unroll 可暴露更多獨立工作，但不保證跨 iteration 流水化成功。

Double buffering 的正確性帳本

  1. Prologue：先請求 tile 0。
  2. Iteration k：在合法範圍內提早請求 tile k+1；等待 tile k 的資料。
  3. 若經 LDS 在 waves 間共享：完成 producer 操作並正確集合，再讀取 tile k。
  4. 完成所有 consumers 對舊 buffer 的使用，才能重用該 buffer。
  5. Epilogue：不讀越界的下一 tile，不遺漏最後一個 tile，不讓 masked tail 破壞 barrier participation。

增加 stage 不只是改一個整數：需要更多 staging VGPR／LDS、較長 live range、更多 outstanding events、程式碼與啟停成本。短 K 或 latency 優先 kernel，深 pipeline 可能更慢。

Initiation interval 的概念下界

II ≥ max(ResMII, RecMII)：resource-constrained minimum II 來自每迭代資源需求；recurrence-constrained minimum II 來自 loop-carried dependency 的 latency／iteration distance。這是 modulo scheduling 的模型；bank conflicts、有限 buffers、實際 memory latency 與不規則控制流仍會提高成本。寫了兩個 buffers，不代表 II=1。

LLM kernel 對映

From tensor shapes to bottlenecks

分析框架 · 非 benchmark

Prefill 和 decode，通常不是同一個最佳化問題。

將線性層寫成 Y[M,N] = X[M,K] × W[K,N]。M 包含本次一起運算的 token／batch 維度；K、N 為輸入與輸出維度。Prefill 往往能重用 W 處理很多 token，較有機會把 GEMM tile 餵飽；單 sequence decode 常接近 M=1 的 GEMV／skinny GEMM，權重讀取與其他 overhead 可能支配成本。Continuous batching、MoE、speculative decoding 會改變 M 與工作分布，不能只看「decode」標籤。

4-bit packed weights 把權重 payload 壓小，但還有 block scales／zero points、packing alignment、dequantization、type conversion 與 padding。GGUF 的某個 Q4／Q5／Q6 格式，不等於 WMMA 的原生 IU4／IU8 layout；可能需解碼到 FP16／FP32 再算，或走專門 dot kernel。是否能直接用 native integer matrix ops，取決於格式與數學定義，而不只 bit width。

Attention / KV cache 的帳

簡化未量化 KV 儲存量：

KV bytes ≈ 2 × layers × sequences × context_length × kv_heads × head_dim × bytes_per_element

前面的 2 是 K 與 V；用 kv_heads，不是必然等於 query heads。此式忽略 padding、page tables、metadata、不同層結構與 sliding-window 等特例。decode 隨 context 增加，KV 掃描可能逐漸主導；即使整個 KV 能放進系統 RAM，也不代表掃描的 bandwidth 與 latency 足夠。

FlashAttention 類演算法把 attention 分塊並使用 online softmax 更新，避免物化完整 score matrix；然而具體 RDNA backend 的 tile／register／LDS 配置，仍需獨立設計與驗證，不是直接搬 CDNA MFMA 或 CUDA warp-group kernel。

Roofline 與流量估算

A model you can challenge

推導模型 · 不是真機預測

先算最低要搬多少資料，再看還有多少空間。

基本 roofline 為 attainable FLOP/s ≤ min(compute ceiling, bandwidth × arithmetic intensity)，其中 AI = operations / bytes。bytes 必須說明是哪一層的流量：DRAM、L2 或 LDS，不同層不能混在同一條 roofline。cache reuse、write-allocate、metadata、重讀與 fusion 都會改變實際 traffic。

矩陣 tile 操作量依據：RDNA 3.5 ISA §7.9。IO-aware 演算法例子：FlashAttention 論文。此章公式及計算器為工程推導。

GEMV：權重主導的簡化

忽略 activation、output、scales 等，矩陣每個權重約做 2 FLOPs：FP16 權重為 2 / 2 = 1 FLOP/byte；4-bit packed 權重為 2 / 0.5 = 4 FLOP/byte。這不是量化 kernel 的完整 AI，因為 unpack 本身不是同樣的 FP 工作，scales 和 padding 也要搬。

若一次 token 的 weight traffic 真的是 B bytes，單就此流量的時間下界是 B / BW_effective。用 peak spec 的 BW 得到的上界會更樂觀；用同機、相近存取模式測出的 sustained bandwidth 才比較有意義。

公式：GB = 參數量(B) × bytes/parameter；ms = GB ÷ (GB/s) × 1000；token/s = (GB/s) ÷ GB。這裡 GB=10⁹ bytes，不是 GiB。

GEMM 的重用如何提高 AI？

對 C[M,N] = A[M,K]B[K,N]，理想一次讀 A、B，寫 C 且不讀舊 C：

FLOPs ≈ 2 M N K
bytes ≈ sA M K + sB K N + sC M N

若需要 beta*C，還要加 C read；若 tile 重複從 DRAM 搬入、量化有 metadata，流量更高；如果 operands 已在 cache，DRAM 流量可更低。增加 M 的 batch reuse 可能明顯提高 AI，但 register／LDS 容量決定能否實現重用。此公式沒有宣稱實際 library 只搬一次。

Amdahl 對端到端優化的提醒

若某 kernel 佔總時間比例 f，只讓它加速 s 倍，理想 end-to-end speedup 為 1 / ((1-f) + f/s)。例如 f=0.2、s=2，只得到約 1.11×。測到某個 matrix kernel 加速兩倍，不代表生成 token 同樣兩倍；也要確認新的瓶頸與 profiler overhead。

實驗 A：同一 LLVM IR，兩個 target

/opt/rocm/llvm/bin/clang --version

for cpu in gfx1150 gfx1151; do
  /opt/rocm/llvm/bin/llc -mtriple=amdgcn-amd-amdhsa -mcpu="$cpu" \
    -O2 -verify-machineinstrs -debug-pass=Structure -o - <<'IR'
define amdgpu_kernel void @scale4(ptr addrspace(1) %p) {
entry:
  %x = load volatile <4 x float>, ptr addrspace(1) %p, align 16
  %y = fmul <4 x float> %x, <float 2.0, float 2.0, float 2.0, float 2.0>
  store volatile <4 x float> %y, ptr addrspace(1) %p, align 16
  ret void
}
IR
done

這是觀察 codegen 的 toy kernel，沒有 work-item indexing，不要任意多 thread dispatch，否則有相同位置讀寫問題。volatile 用來保留讀寫，也會影響 memory legalization；不能拿它的 wait 數代表一般 kernel。

五類定位問題

問題 優先證據 謹慎之處
CPU／launch bound？ API trace、dispatch 間空隙、端到端 vs device time CPU API duration 不是 GPU kernel duration
DRAM／cache bound？ sustained BW、working-set sweep、可用 cache counters hit rate 高不等於 bandwidth 足夠
ALU／WMMA bound？ 指令組成、依賴鏈、可用 utilization/counter 指令數不是 cycle 數
Register／LDS bound？ metadata、scratch、tile／unroll 門檻掃描 occupancy 只代表駐留能力
Barrier／imbalance？ wave/group 工作量、同步位置、tail、分工 刪 barrier 不是合法最佳化

可重現 A/B 最小紀錄

  • GPU SKU、target、driver／OS、ROCm／compiler commit、kernel／llama.cpp commit。
  • 模型及量化格式、shape、batch、context、KV dtype、prompt／decode 分段。
  • flags、wave size、tile、unroll、stages、VGPR／SGPR、LDS、scratch。
  • 暖機、重複次數、A/B 交錯順序、功耗／時脈／溫度狀態、CPU/DRAM 競爭。
  • median、分布／離群原因；同時報 absolute time、相對變化、correctness tolerance。

不要把 A 的冷啟動和 B 的暖 cache 比，也不要讓 profiler 重放／instrumentation overhead 混進正式 latency。共享 DRAM APU 尤其要隔離 CPU memory traffic；cache-resident 小問題與大模型 streaming 是兩種 workload。

Microbenchmark 的設計對照

Latency 用 dependent chain；throughput 用獨立 accumulators；cache 掃 working-set／stride；LDS 固定 access width、改 lane-to-bank mapping；occupancy 掃 live VGPR／LDS、查 metadata 是否真變；software pipeline 檢查 prologue／steady／epilogue 與 waits，再測不同 K。每個實驗只主張它量到的範圍。
