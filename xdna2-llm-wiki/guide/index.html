01 / THINK IN SPACE & DATAFLOW

不是小 GPU。是編譯器排好班的 tile array。

32

Compute tiles

NPU2 模型為 8 欄 × 4 計算列。每核執行自己的程式；核心不是一個 warp 的 lane。[1]

64 KiB

每個 compute tile 的 L1

軟體管理 SRAM，不是透明 cache。FIFO buffers、stack、常數與 globals 都要占空間。[14]

512 KiB

每個 memory tile 的 L2

用於 staging、重排與廣播。L1/L2 是分散 scratchpads，不能當成一塊任意可存取的大 cache。[3]

一欄裡的三種工作：點選切換

Compute tile：算，也負責本地控制

Scalar control + SIMD/vector 計算 + VLIW 指令 bundle。從本地 SRAM 載入向量，送入 multiply/accumulate 路徑；與 DMA、鄰近 tile、stream switch 配合。

VLIW：一個 cycle 裡做多件事

AI Engine 是 in-order、exposed-pipeline 處理器；compiler 必須知道運算延遲、register 使用時刻與 issue slots，安排 load、compute、store 的重疊。Peano 甚至要處理 negative operand latency 與特殊 register hierarchy。

這不同於讓大量 GPU wavefronts 由硬體輪替隱藏延遲；也不代表整個 NPU 永遠不會阻塞，stream／lock／DMA 等待仍然存在。[4]

Spatial dataflow：搬運本身也是程式

Host DRAM → Shim DMA → MemTile → Compute L1 → vector registers → accumulator。結果可回到 memory tile，也可透過專用 cascade 路徑傳遞中間累加值。

acquire()／release() 描述資料生命週期；ObjectFifo lowering 產生 buffers、locks、DMA。它不是 Python queue 在 NPU 上執行。[7]

gfx1151 ≠ AIE2P
gfx1151 是 Strix Halo 內 RDNA 3.5 iGPU 的 GPU target；XDNA 2 NPU 用 npu2 device model 與 aie2p core target。共享系統 DRAM，不代表可以把 GPU pointer 或 HIP binary 直接交给 NPU。新 runtime 的 zero-copy 是另外一層映射與同步機制。

文件閱讀注意：AIE2P（arch 21）≠ AIE2PS（arch 22）。AM027 的 Versal AIE-ML v2 不是可直接當成 Ryzen XDNA2 指令集手冊的同一 target，尤其不可移植它的 FP16／FP8 型別支援結論。本文以 NPU2 device model 與 AIE2P headers 為準；AMD Hot Chips 的 XDNA 2 簡報另已下載。[15]

有這個 type，不代表有這個 type 的原生 MMA。

必須拆成三層：能表示／搬運 → 有 intrinsic 或 emulation → frontend 有可用 mapping 與驗證範例。下表針對 AIE2P 的矩陣乘法，不是列出 Clang 所有語言型別。[6][8]

BFP8：本次未證實未找到 AIE2P 獨立 BFP8 block-vector／MMUL 登錄。不能把 BFP16 的 8-bit mantissa 改叫 BFP8。arch 22 的 bfloat8 / float8 不是 XDNA2 AIE2P 支援證據。
FP32 × FP32矩陣乘法由 BF16 運算 emulation，不是原生完整 FP32 MMAFP32 輸出／accumulator ≠ FP32 input multiplication precision。Triton padded f32 範例明示 BF16 emulation；不能推論符合完整 IEEE FP32 matmul。
FP16 / IEEE FP8 / FP64本文查核的 AIE2P mmul 表未證實直接原生模式需 conversion／software lowering 或其他 device。「沒有查到 native MMA」不等於任何 load/store 或 scalar operation 都不支援。

BF16 ≠ BFP16

BF16 每個元素各自有 exponent。BFP 把一群數值共用 exponent，以較窄的尾數表示整個 block；outlier 可能讓同組小數值失去有效位元。

AIE_API_EMULATE_BFLOAT16_MMUL_WITH_BFP16 是從 BF16 語意介面切到 BFP16 計算的選項，明確以 accuracy 換 throughput。[6]

FP32 的兩種「看起來支援」

① BF16 × BF16 → FP32 accumulation：輸入仍是 BF16。② float × float：API 以 BF16 multiplications 合成；而 Triton 的 emulation 選項可以先將 f32 截至 bf16。

它們不是同一個數值模型。需要比較誤差、輸入範圍與轉換設定，而不只看 output dtype。[5][6]

AIE API 文件的 superscript a/b/c/e 分別涉及多 intrinsic、額外資料處理、32-bit 乘法合成與 BFP emulation。查 support table 時不能把註腳省略；headers 和本次固定版本的 kernel 才是實作依據。

Source audit 抓到的三個陷阱
  • INT4：API 不等於原生指令。mul_4x16_16x16 這個「intrinsic」wrapper 在本 Peano 中先 unpack，再執行兩次 INT8 運算。
  • BF16 4×8×8 並非一條 matrix 指令。非 BFP 的 AIE API helper 使用 8 次 32-lane BF16 MUL/MAC 加上 shuffle/broadcast。直接 MLIR AIEVec lowering 的相同表面 shape 則可轉成 BFP16。
  • BFP16 名字不是儲存位元數。EBS8 格式為每 8 個 signed 8-bit mantissa 共用 8-bit exponent：9 bytes / block，64 個值合計 72 bytes。EBS16 緊縮記憶體格式與 register representation 又不同。

逐條 immutable 原始碼、行號、signedness、accumulator、rounding 與 emulation 展開見 獨立查核報告。這也說明為什麼不能直接抄 architecture cheatsheet 的 BF16 MAC/cycle 數字。

完整程式要解決四層 tiling

01 · HOST
全矩陣 M×K×N系統記憶體中的矩陣。Host 排列通常 row-major。
02 · ARRAY
分工給 rows × columnsM/N 分配 output tiles；A/B 廣播重用，避免重複 DDR 讀取。
03 · COMPUTE TILE
每核 m×k×nL1 buffer + double buffering；K 分段累加。
04 · VECTOR
microtile r×s×t預先 packing 成 intrinsic 的 operand layout，再 mmul/mac。

不要讓核心忙著搬矩陣

Host row-major 的一個 64×64 block，不等於一連串 microtile 的記憶體順序。可用 MemTile 的多維 DMA，把 transfer 同時做成 tile packing／transpose，再讓 core 用連續 vector loads。

# A block (m,k) → 一串 (r,s) microtiles
# IRON dims_to_stream 示意；以目前 API element units 為準
[
  (m // r, r * k),
  (k // s, s),
  (r, k),
  (s, 1),
]

MemTile BD 支援 4 維 addressing；core/shim BD 為 3 維。不能把 4D reshape 任意放到任何 DMA。重排可減少 core 指令，但不代表 bus、descriptor 與 bandwidth 成本為零。[3][7]

Reuse、pipeline、cascade

  • 多 accumulator blocking：一次載入 A/B 後更新多個 C subtiles，提高 data reuse，避免 accumulator dependency 限制 issue。
  • Double buffering：第 i 塊正在算時，DMA 填第 i+1 塊；FIFO 深度、bank 分配與鎖時序一起設計。
  • Software pipelining：讓 load / MAC / store 在不同迭代間重疊；__restrict 幫助 alias 分析。
  • Cascade reduction：用專用串流傳遞 partial accumulators，不必每段都轉成較低精度寫 SRAM。但本次 IRON cascade_mm 範例仍是 scalar-only，不能宣稱已有高效 vector cascade GEMM。

[7][8]

Sparse MMA 是另一條路：AIE API 列有 XDNA 2 的 sparse-B integer matmul，例如 INT8 的 4×16×8、8×16×8。需要支援的壓縮 layout 與 sparse operand，不是把 dense tensor 中部分元素設成零就自動加速；也不要把 XDNA 1 的 BF16 sparse 模式搬到 XDNA 2。[6]

一個最小 BF16 C++ microkernel

教學用：A 有 32 個 BF16，B 有 64 個 BF16，C 有 32 個 FP32；各小矩陣在自身 block 內 row-major，指標至少 64-byte 對齊。只算一個 microtile，不含 host、DMA、placement 或大型矩陣外圈。

以下非 BFP 解釋假設 AIE_API_EMULATE_BFLOAT16_MMUL_WITH_BFP16 未定義。若啟用，數值路徑會改變；請同時閱讀 audit 中的 rounding mode save／set／restore 範例。

// AIE2P C++ fragment. Source-level checked, not compiled here.
#include <aie_api/aie.hpp>

extern "C" void bf16_tile(const bfloat16* __restrict a,
                           const bfloat16* __restrict b,
                           float* __restrict c) {
  using MM = aie::mmul<4, 8, 8, bfloat16, bfloat16, accfloat>;
  auto av = aie::load_v<MM::size_A>(a);
  auto bv = aie::load_v<MM::size_B>(b);
  MM sum;
  sum.mul(av, bv);  // C := A * B
  // More K blocks: sum.mac(next_a, next_b);
  aie::store_v(c, sum.to_vector<float>());
}

整數寫回則還涉及 to_vector<T>(shift)、rounding 與 saturation 設定。accauto 的決定依 operand type／target，不能把所有整數都假設成 acc32。[6]

L1 工作集估算器

沿用上面的 dtype。假設 A/B 各雙 buffer、C 一個 32-bit buffer、1 KiB stack。BFP 路徑仍儲存 BF16 輸入。這只是容量初篩，不是 compiler legality check 或效能預測。

L1 bytes = 2 × (m·k + k·n) × inputBytes + m·n × 4 + 1024
通過仍可能因 bank conflict、alignment、globals、額外 buffers、compiler spills 或 kernel expansion 限制而失敗。

air.herd 表示並行 worker 網格，air.channel.put/get 表示搬運端點，token 表示依賴。Compiler 可以用這些資訊安排資料與 compute 的重疊，不必由 host 每一小步同步。[10]

  • tt.shared.mlir：Triton shared/Linalg 表示。
  • air_project/：AIR lowering 中間資料。
  • aie.mlir、input_with_addresses.mlir：tile 配置與位址。
  • main_core_<col>_<row>.ll/.o/.elf：per-core code。
  • final.xclbin、insts.bin、main.pdi：IRON 常見產物。

Runtime 不只一條

IRON 文件以 XRT xclbin + instruction stream 為主要示範。當前 Triton-XDNA README 指出 XRT 預設 NPU2 使用 ELF，也新增 Linux HSA/ROCr 的 AIE agent dispatch。

HSA 需要 AIE-capable ROCr，不能假設既有 ROCm 安裝就有。GPU/NPU 共用 PyTorch process 還要防範載入錯誤版本的 ROCr。這不是把 NPU 當 HIP GPU。[5][9]

Open-source 範圍：這裡選 Peano，不要求專有 Chess／Vitis license。Compiler 原始碼開源，不等於 BIOS、NPU firmware、所有 driver packaging 或 Ryzen AI model runtime 都是同一授權，也不表示整個硬體平台完全 open-source。

Step 1 · IRON vector add：學會資料生命週期

這是自 README 改寫的可讀範例，加上明確 NPU2 device 與結果檢查。Python 函式建立 MLIR design；NPU 上不是在跑 CPython。

import numpy as np
import aie.iron as iron
from aie.iron import In, Out, ObjectFifo, Program, Runtime, Worker
from aie.iron.controlflow import range_
from aie.iron.device import NPU2

data_ty = np.ndarray[(1024,), np.dtype[np.int32]]

@iron.jit
def add_one(a_in: In, b_out: Out):
    incoming = ObjectFifo(data_ty, name="in")
    outgoing = ObjectFifo(data_ty, name="out")

    def core_fn(src, dst):
        a = src.acquire(1)
        b = dst.acquire(1)
        for i in range_(1024):
            b[i] = a[i] + 1
        src.release(1)
        dst.release(1)

    worker = Worker(core_fn, [incoming.cons(), outgoing.prod()])

    def sequence(a, b, src, dst):
        src.fill(a)
        dst.drain(b, wait=True)

    runtime = Runtime(sequence, [data_ty, data_ty,
                                incoming.prod(), outgoing.cons()])
    return Program(NPU2(), runtime, workers=[worker]).resolve_program()

a = iron.arange(1024, dtype=np.int32, device="npu")
b = iron.zeros(1024, dtype=np.int32, device="npu")
add_one(a, b)  # first call compiles; subsequent calls may hit cache
np.testing.assert_array_equal(np.asarray(b), np.arange(1024) + 1)

這段用來學 control flow 與 FIFO，不宣稱自動成為最佳向量化 kernel。若先執行原版範例，可從 programming_examples/basic/vector_scalar_add/vector_scalar_add.py 開始。[2]

cd /home/chihmin/xdna2-lab/sources/mlir-aie

python3 whole_array.py --dev npu2 --n-aie-cols 8 \

06 / MAKE IT FAST — AND CORRECT

TOPS 是天花板，不是你的程式速度。

AMD 的 XDNA 2 簡報列出 50 INT8 TOPS 與 50 Block FP16 TFLOPS 級峰值；後者不是 50 TFLOPS 原生 BF16 或 FP32。每個 SKU、時脈、功耗與可用 tiles 都會影響可達值。[15]

COMPUTE

GEMM arithmetic intensity

用 2MNK 計算數學 operations，再除以實際 DDR traffic。理想情況 bytes 約為 MK·a + KN·b + MN·c；重載、padding、packing 與 cache/mapping 會改變真實流量。

DATA MOVEMENT

看重用，不只看核數

多用一倍 tile 可能增加 broadcast、BD 與同步壓力。單 token decode / GEMV 通常比大 batch prefill GEMM 更容易被權重 bandwidth 或 launch overhead 限制。

END TO END

冷編譯 ≠ 暖執行

分開記錄 JIT compile、buffer allocation/mapping、copy、device execution、同步與驗證。要做 GPU/NPU 比較時，至少對齊精度、shape、batch、資料駐留與功耗。

建議的實驗順序

  1. 先正確：小尺寸、固定 seed，INT 使用寬整數 reference；BF16/BFP 明列 atol、rtol、最大／平均誤差，加入 outlier、負數與極小值。
  2. 再看 core：讀 per-core ELF disassembly 與 pipeline schedule，確認真的產生矩陣乘加，而非 scalar loop。檢查 spills、dependency chains 與 vector loads。
  3. 調 tile 與 buffer：從單 core 到單欄，再到多欄。記錄 L1 占用、bank 分配、FIFO depth 與 BD 數目。
  4. 看 trace：使用上游 trace / Perfetto 流程，區分 core 空等、DMA 飢餓、lock 阻塞與 host launch。
  5. 最後比端到端：暖機後多次測量中位數與分位數，另列冷啟動；每個結果附 commit、dtype、M/N/K、clock/power 配置。
研究 benchmark，不冒充本機 benchmark：GEMM 論文在其 XDNA2 測試平台報最高 38.05 TOPS INT8、14.71 TOPS BF16；不同 output precision 與不同 shape 的結果不能混用。論文使用的 XDNA2 主機為 Ryzen AI 7 350，而非這台 Strix Halo；本次也沒有證實其最佳數字全都来自 Peano-only flow。[11]

對本機 gfx1151 / XDNA2 的合理分工

先讓 GPU 繼續處理成熟 HIP/ROCm workload。選一個固定形狀、足夠高 reuse 的 INT8／BF16 operator，在 NPU 上建立 correctness + warm latency baseline。只有在包含 dispatch、資料交接與同步後仍划算，才考慮拆分整個模型。不要把 NPU 的 50 TOPS 直接加到 GPU FLOPS 上，宣稱 LLM 會快某個比例。
